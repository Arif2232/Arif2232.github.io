A workflow should survive
a repeated request.

A practical design note on reliable automation, using a training and onboarding workflow as the example.

This is a small demonstration created for this portfolio, with an accompanying proposed architecture. It is separate from the professional work described on the homepage.

The problem

A training request can arrive twice. An API can time out after accepting it. A worker can fail midway through processing. Treating each retry as a new request can produce duplicate work, inconsistent state and a confusing support trail.

The starting point is a durable record with a stable idempotency key. Reusing the key with identical content returns the existing task; reusing it with different content is an error. That makes an ambiguous retry distinguishable from a genuinely new request.

A runnable slice

The accompanying example uses only Python’s standard library. A SQLite transaction commits task state and its audit event together. Multiple database connections share the same unique request key, and completing a task twice does not duplicate its completion event.

What I would add for a real training workflow

ConcernDesign choice
External side effectsUse the provider’s idempotency key and store its receipt. A local transaction alone cannot guarantee exactly-once delivery to an external service.
Multiple workersAdd atomic claims, expiring leases and ownership tokens so an expired worker cannot overwrite a newer result.
Uncertain AI outputLet a model classify a request or draft learning content against a schema. Validate the result and route uncertain or consequential changes for human review.
RetriesDistinguish transient failures from invalid requests, use bounded exponential backoff and retain a reviewable failure state after the retry budget is exhausted.
OperationsMeasure queue age, success and retry rates, and completion latency. Keep sensitive payloads out of routine logs.

The boundary that matters

A confirmed external receipt, an uncertain result and a failed request are different states. I would preserve that distinction in the data model and the interface. If a request times out after it may have succeeded, the next action should be reconciliation with the provider rather than an unconditional second send.

The sample implements the local persistence and deduplication portion. Worker coordination, model integration and external delivery are design extensions, not features claimed by the example.
